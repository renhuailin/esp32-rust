## 2026-08-18 修复播放时偶发"嗒嗒嗒"卡死（整机无响应）

### 现象

设备播放 TTS 音频期间，**偶发**（不是每次）出现以下症状组合，只能断电重启：

1. 扬声器持续"嗒嗒嗒嗒"响，无法停止；
2. 设备完全无响应（按键失效，无法停止播放）；
3. 服务器端音频仍在源源不断下发（websocket 连接正常）。

### 排查过程

#### 1. 从症状组合提取关键线索

三个症状看似矛盾（设备"死了"但网络"活着"），恰好构成精确的诊断依据：

| 症状               | 推论                                                                 |
| ------------------ | -------------------------------------------------------------------- |
| 嗒嗒声不停         | I2S TX DMA 在无人喂数据的状态下循环输出最后的残留 buffer（underrun） |
| 整机无响应         | **主循环线程**卡死（按键事件、websocket 消息都由它处理）             |
| 服务器音频仍在下发 | websocket 收包是独立线程，不受主循环卡死影响                         |

→ 问题定位为：某线程持锁永久阻塞，把主循环锁死了。

#### 2. 梳理播放链路与锁的持有关系

播放链路（会话模式）：

```
websocket 收包线程 → 主循环(AudioPacketReceived) → audio_decode_queue(入队)
audio_loop 线程 → start_audio_output() → mem::take(队列) → decode_opus_audio()
                → codec.lock() → output_data() → i2s write(chunk, BLOCK)
```

审读 `xiaozhi_audio_codec.rs` 时发现致命写法：

```rust
// output_data / test_play_pcm
i2s_driver.lock().unwrap().write(chunk, BLOCK)   // BLOCK = portMAX_DELAY，永久阻塞！
```

#### 3. 还原死锁链条

```
① 播放中 I2S TX DMA 偶发停摆（诱因，偶发所以"有时候"才出现）
② audio_loop: output_data() 里 write(chunk, BLOCK) 永久阻塞
   → audio_loop 卡死，codec 锁被永久持有
③ 主循环收到 tts stop → play_silence() → codec.lock() 拿不到锁
   → 主循环永久卡死 → 按键/停止全部失灵 = "设备卡死"
④ DMA 停摆前最后的残留 buffer 循环输出 = "嗒嗒嗒"不停
⑤ websocket 收包线程独立存活 = "服务器端还有音频过来"
```

连锁放大机制：**单条 write 的无限阻塞 → 线程卡死 → 锁被永久持有 → 锁死主循环 → 整机瘫痪**。

#### 4. 附带发现的隐患

`read_audio_data` 的读超时写的是 `1000` ticks。本项目 `CONFIG_FREERTOS_HZ` 使用 IDF 默认值 **100Hz**（`sdkconfig.defaults` 里 1000Hz 被注释掉了），1 tick = 10ms，即 **1000 ticks = 10 秒**——远超预期（写代码的人大概率以为是 1000ms）。RX 若卡住，audio_loop 会持 codec 锁 10 秒，播放随之断流。

### 修复

`src/audio/codec/xiaozhi_audio_codec.rs`：

1. 新增 tick 换算（从 esp-idf-sys 生成的 bindings 读取 `configTICK_RATE_HZ`，不硬编码）：

```rust
const fn ms_to_ticks(ms: u32) -> u32 {
    let t = ms * esp_idf_sys::configTICK_RATE_HZ / 1000;
    if t < 1 { 1 } else { t }
}
const I2S_WRITE_TIMEOUT_TICKS: u32 = ms_to_ticks(250);
const I2S_READ_TIMEOUT_TICKS: u32 = ms_to_ticks(500);
```

2. `output_data()` / `test_play_pcm()`：`BLOCK` → `I2S_WRITE_TIMEOUT_TICKS`（250ms）。
   超时即打 `I2S TX stalled` 错误日志并丢弃本包剩余数据，**尽快释放 codec 锁**。
3. `read_audio_data()`：`1000` ticks → `I2S_READ_TIMEOUT_TICKS`（500ms）。

效果对比：

|        | TX 停摆一次的后果                                              |
| ------ | -------------------------------------------------------------- |
| 修复前 | 整机死锁，只能断电重启                                         |
| 修复后 | 丢一个音频块（≤几百毫秒）+ `I2S TX stalled` 日志，设备继续可用 |

配合 2026-08-15 为 tts stop 增加的"排空等待 + 3 秒超时兜底"，整条播放链路已无永久阻塞点。

### 踩坑记录（编译层面）

- `esp_idf_sys` 的 bindings **没有**导出 `portTICK_PERIOD_MS`（只在 doc 注释里出现），但有 `configTICK_RATE_HZ`。换算用后者。
- `u32::max()` 不是 const fn，不能用在 `const` 定义里，需要手写 `const fn` 分支。

### 验证

烧录后正常使用，重点观察：

1. 长时间播放是否还出现嗒嗒响；
2. 若再出现，设备此时**是否还能响应按键**（应该能——这是本次修复的验证点）；
3. 日志中搜 `I2S TX stalled`：出现即命中真凶，且系统按设计降级而非死锁。

### 遗留问题

TX DMA 偶发停摆的底层诱因（AXP173 供电毛刺 / ES8311 / DMA 竞争）暂无法远程定位。
修复后再复现时日志会留下 `I2S TX stalled` 现场，届时可进一步追查。

## 2026-08-19 修复 Speaking→Listening 切换慢（每次 TTS 结束都要等 ~3 秒）

### 背景

为修播放卡顿引入的抗抖动措施（播放 channel 10→25 包、软件 jitter buffer 240ms 起播、
epoch 播放代数、tts stop 排空等待）生效后，出现新问题：**每次 TTS 播完，切换到
Listening 状态明显变慢**。且日志中偶见 `TTS drain timeout, dropping tail packets`。

播放水位机制回顾：发送侧累加 `pcm_sent_bytes`，播放线程写完 I2S 后累加
`pcm_played_bytes`，tts stop 的排空等待要求队列空 + 播放 idle + jitter 空 +
`sent == played`（3 秒超时兜底）。

### 排查过程：两次诊断，第二个才是真凶

#### 诊断一：稳态库存过深（合理优化，但不是主因）

channel 扩到 25 包（1500ms）后，网络突发时解码远快于实时播放，channel 会被
填满——稳态库存变成 1.5s。排空等待必须等"已送出的音频全部写完 I2S"，
切换延迟 ≈ 稳态库存时长。

修复：**库存削峰**。audio_loop 送包前检查水位（`pcm_sent - pcm_played`），
超过高水位 `PLAYBACK_BACKLOG_LIMIT_BYTES = 19200`（300ms @ 64KB/s）就暂停
送包、剩余包放回解码队列队头，下轮再送。要点：

- 不 sleep，只让出本轮输出处理，不影响同线程的拾音喂料节拍；
- channel 的 25 包容量保留作突发兜底，但稳态下永远用不满——
  流畅性不减（300ms 库存比 jitter 起播的 240ms 还深），排空尾长恢复敏捷。

#### 诊断二：计数器被开机提示音"毒化"（真凶，日志实锤）

用户日志：

```
I (167789) 处理文本消息结束: {"type": "tts", "state": "stop", ...}
W (170829) TTS drain timeout, dropping tail packets
I (170919) Listening state changed from Speaking to Listening
```

167789 → 170829 = **3040ms，正好打满 3 秒超时**。超时不是"排得慢"，
而是排空条件**从开机起就永远不可能成立**：

```
① 开机进入事件循环必播 audio_alert("success") 提示音（play_p3_data 路径）
② play_p3_data 往 channel 发包，但不累加 pcm_sent_bytes
③ 播放线程收到包必累加 pcm_played_bytes（无论播放还是按 epoch 丢弃）
④ 从开机那一刻起 played 永久 > sent（差值 = 开机音全部字节）
⑤ 排空条件 sent == played 永远为 false → 每次 tts stop 都白等 3 秒超时
```

这类"水位计数"机制的隐藏陷阱：**只要存在一条不配对的发送路径，
排空条件就被永久毒化**——而且症状（切换慢）与病因（开机提示音）
相隔整个开机过程，极难联想到一起。

### 修复（两处，双保险）

`src/application.rs`：

1. **配对修复**：`play_p3_data` 发送成功后同步累加 `pcm_sent_bytes`，
   与播放侧计数严格配对；
2. **防御修复**：排空条件 `sent == played` 改为 `sent <= played`
   （"已送出的全部消费完"）。即使将来再出现未配对的发送路径，
   排空也能正常收敛，不会再被打满超时。

### 效果

配合削峰（稳态库存 ≤300ms），Speaking → Listening 切换 = 尾包播完
（~0.3-0.5s），不再有 3 秒惩罚；日志中不应再出现 `TTS drain timeout`。

### 经验总结

- 水位/计数配对机制要求**所有**生产者累加、所有消费者扣减，任何一条
  旁路都会让条件永久失效——防御性写法是单向比较（`<=`）而非严格相等；
- "每次都慢固定 ~3 秒" + 超时日志 = 排空条件不收敛的铁证，先查条件
  本身是否可达，再查库存深浅；
- 流畅性（库存深）与响应性（排空快）是天然权衡，削峰 + 突发兜底容量
  可以两全。

## 2026-08-19 播放链路抗抖动机制架构总览（温故知新）

### 背景

前几轮修卡顿、修卡死、修切换慢的过程中，陆续引入了 jitter buffer、epoch
代数、水位计数、削峰等机制。单独看每一条都不复杂，但它们是**协同工作**
的——每个机制只负责扛一个层级、一个量级的抖动。本文把整套架构串起来，
作为后续改动的地图。

### 核心思想：分层抗抖

不同来源的抖动量级完全不同，试图用一层缓冲扛所有抖动必然顾此失彼
（教训：加深 DMA 描述符至 16 导致拾音失效，只能回退）。
正确做法是把抖动拆到链路各层，每层只扛自己最擅长的：

```
WebSocket 收包
    │
    ▼
audio_decode_queue (Mutex<VecDeque>)          ← 网络层缓冲
    │   audio_loop 线程：opus 解码
    ▼
jitter_buffer (VecDeque, 起播攒包)            ← ① 起播抗抖
    │   攒够 240ms 才开始放行
    ▼
sync_channel(25 包 / 1.5s)                    ← ② 突发容量 + 背压
    │   pcm_player_thread
    ▼
I2S TX DMA (auto_clear=true)                  ← ③ underrun 兜底
    ▼
扬声器
```

### 五个机制逐一拆解

#### ① 软件 jitter buffer（起播攒包）

`src/application.rs` `start_audio_output` 内，`JITTER_TARGET_BYTES = 15360`。

新一轮 TTS 的音频**不立刻播**，先攒够 240ms 才开闸（`jitter_primed = true`），
之后随到随放。起播初期是抖动伤害最大的阶段——缓冲薄，一个网络抖动就断流，
断流就是"衔接卡顿"。攒够 240ms 后，播放线程身后永远有 240ms 的储备可透支。

为什么用软件而不是加深 DMA：DMA 描述符加深实测破坏拾音（见上文教训），
软件缓冲想多深就多深，代价只是内存。

#### ② sync_channel(25) —— 突发容量 + 天然背压

```rust
let (pcm_tx, pcm_rx) = std::sync::mpsc::sync_channel::<(usize, Vec<u8>)>(25);
```

解码侧快于实时播放时（网络突发，一秒内涌来好几秒的包），channel 提供
最多 25 包 ≈ 1500ms 的**瞬时容量**；满了 `send()` 自动阻塞解码侧——
这就是**背压**（backpressure），不需要手写任何限速代码，消费速度天然
反压生产速度。有界队列是嵌入式里最简单可靠的生产限速手段。

注意：1500ms 只是突发上限，配合⑤削峰，稳态库存收敛在 ~300ms，
不会拖慢 tts stop 排空（切换慢的教训见上一天日志）。

#### ③ auto_clear —— DMA underrun 兜底

`src/boards/jianglian_s3cam_board.rs`：

```rust
let std_config = StdConfig::new(
    Config::default().auto_clear(true),
    ...
);
```

这是"嗒嗒嗒"的直接杀手。即使有 jitter buffer，网络仍可能短暂断流，
导致 I2S TX DMA **underrun**（没有新数据可发）。`auto_clear = false` 时
DMA 会**循环重发最后一个缓冲的残留片段**（~32ms）——断流 1 秒就变成
1 秒的"嗒嗒嗒"；`auto_clear = true` 则自动发静音，听感上只是一次轻微停顿。

#### ④ epoch 播放代数（打断快切）

每个包发送时烙上当时的代数 `play_epoch`（`AtomicUsize`）。用户打断
（`abort_speaking`）时 `play_epoch += 1`，播放线程发现包的代数过期就直接
丢弃不写 I2S：

```rust
for (epoch, pcm_packet) in pcm_rx {
    let cur_epoch = audio_state.play_epoch.load(Ordering::SeqCst);
    if epoch == cur_epoch {
        codec.lock().unwrap().output_data(&pcm_packet).unwrap();
    }
    // 丢弃也要计数 played，保持水位配对
    audio_state.pcm_played_bytes.fetch_add(pcm_packet.len(), Ordering::SeqCst);
}
```

没有它，打断后 channel 里库存的最多 1.5s 旧音频还会继续播出来。
**关键设计：旁路数据用代数标记丢弃，而不是清空队列**——清队列有竞态
（清完瞬间又来了新包），代数比对是幂等且无锁的。

#### ⑤ 水位计数 + 削峰（排空判断 + 稳态库存控制）

- **水位计数**：发送侧累加 `pcm_sent_bytes`（所有发送路径都要加！），
  播放侧写完 I2S 或按代数丢弃后累加 `pcm_played_bytes`，差值 =
  "已送出未播完"的库存量。tts stop 排空等待据此判断尾音是否播完；
- **削峰**：送包前检查水位超过 `PLAYBACK_BACKLOG_LIMIT_BYTES = 19200`
  （300ms）就暂停送包、剩余包放回解码队列队头。稳态库存压在 300ms，
  既保流畅（比 240ms 起播线还深）又让排空敏捷。
  不 sleep，不影响同线程的拾音喂料节拍。

### 图解：六张图看懂整套机制

#### 图 0：抖动的根源——两个时钟各跑各的

```
网络侧时钟（服务器下发节奏）:
  ████░░░░██████████░░░░░░░████░░░░██   ← 忽快忽慢（几百 ms 量级抖动）

播放侧时钟（I2S DAC 消耗节奏）:
  ████████████████████████████████████   ← 恒速 64KB/s，从不等待

两个时钟没有任何同步机制 → 必须在中间垫缓冲：
  网络快阶段：数据涌来 → 得有地方存（jitter buffer / channel 吸收）
  网络慢阶段：数据断供 → 得有东西垫（库存透支 / DMA 静音兜底）
```

#### 图 1：全景架构——五道防线各就各位

```
WebSocket 收包线程
    │
    ▼
audio_decode_queue (Mutex<VecDeque>)         [网络层缓冲]
    │  audio_loop 线程：opus 解码
    ▼
┌─ jitter_buffer ──────────────┐             ① 起播攒包 240ms（JITTER_TARGET_BYTES）
│  攒够才开闸，身后常备库存      │
└──────────────────────────────┘
    │
    ▼
┌─ sync_channel(25 包 / 1.5s) ─┐             ② 突发容量 + 满则 send() 阻塞（天然背压）
│  有界队列，满了自动反压解码侧  │             ⑤ 送包前查水位，>300ms 削峰
└──────────────────────────────┘
    │  pcm_player_thread（按 epoch 比对）    ④ 代数过期直接丢弃
    ▼
┌─ I2S TX DMA (auto_clear) ────┐             ③ underrun 自动发静音（防嗒嗒嗒）
└──────────────────────────────┘
    ▼
  扬声器（恒速消耗）
```

#### 图 2：jitter buffer——起播攒包，给播放线程攒"过冬粮"

```
TTS 首包到达，不开闸，先攒：

  攒包中（jitter_primed = false）
  ┌────────────────────────────┐
  │ ████████████░░░░░░░░       │   未攒够 240ms，播放线程干等
  └────────────────────────────┘
            │ 攒够 15360 字节
            ▼
  开闸（jitter_primed = true）
  ┌────────────────────────────┐
  │ ████████████████████       │   边播边补，库存始终 ≥ 弹性水位
  └────────────────────────────┘

之后网络哪怕断流 240ms，播放线程身后都有储备可透支——
起播初期（缓冲最薄）恰恰是抖动伤害最大的阶段，所以把攒包放在最前面。
```

#### 图 3：sync_channel 有界队列——免费的背压

```
解码侧（快，突发）              播放侧（慢，恒速）
     │                              ▲
     │ send()                       │ recv()
     ▼                              │
   ┌──────────────────────────┐
   │ ▓▓▓▓▓▓▓▓▓▓▓▓▓ 25 个槽位   │
   └──────────────────────────┘

  队列未满：send() 立即返回，解码全速跑
  队列已满：send() 阻塞 ← 背压！生产速度被消费速度天然反压

不需要手写任何限速代码：一秒涌来三秒的包，channel 先吃下 1.5s，
解码侧随即被阻塞等到播放侧消化——有界队列是最简单可靠的生产限速。
```

#### 图 4：auto_clear——DMA underrun 的两种命运

```
播放线程没跟上，DMA 描述符耗尽（underrun）：

  ┌──────────────────────────────────────┐
  │ auto_clear = false（默认）            │
  │   DMA 循环重发最后 buffer 的残留片段   │
  │   (~32ms) ──► "嗒嗒嗒嗒嗒嗒"         │
  │   断流 1 秒 = 嗒嗒声 1 秒             │
  ├──────────────────────────────────────┤
  │ auto_clear = true（本项目）           │
  │   DMA 自动发送静音 ──► 一次轻微停顿    │
  └──────────────────────────────────────┘

这是"嗒嗒嗒卡死"事故的直接杀手：上层缓冲再多，也挡不住
最后一米（DMA）的瞬时断供，兜底必须放在硬件层。
```

#### 图 5：epoch 播放代数——旁路数据"自证过期"

```
正常播放：
  发送侧烙 epoch=7 ──► 包到达 ──► 当前 play_epoch=7 ──► 相等，写 I2S ✓

用户打断（abort_speaking）：play_epoch: 7 ──► 8（AtomicUsize 原子自增）

  旧代数包：epoch=7 ──► 当前 play_epoch=8 ──► 不等，直接丢弃 ✗
  新代数包：epoch=8 ──► 当前 play_epoch=8 ──► 相等，正常播放 ✓

为什么不清空队列：
  清队列方案：清完的瞬间新包又入队 ──► 竞态窗口，需加锁
  代数方案：  旧包自己携带"过期身份证" ──► 无锁、幂等、零竞态
```

#### 图 6：水位计数 + 削峰——稳态库存的天花板

```
发送侧                                播放侧
pcm_sent_bytes ──┐                  ┌── pcm_played_bytes
   (累计 128000)  │    backlog =     │    (累计 108800)
                  │    sent - played │
                  ▼                  ▼
              ┌─────────────────────────────┐
              │   已送出、未播完的库存         │
              │   19200 字节 = 300ms          │◄── PLAYBACK_BACKLOG_LIMIT_BYTES
              └─────────────────────────────┘

  backlog < 300ms：正常送包
  backlog ≥ 300ms：本轮停止送包，剩余包放回解码队列队头（削峰）

  tts stop 排空判断：sent <= played 即"已送出的全部消费完"
  （用 <= 而非 ==：防御任何未配对发送路径把条件永久毒化）

效果：流畅性靠 240ms 起播库存，响应性靠 300ms 稳态天花板，
1.5s 的 channel 容量只留给真正的网络突发——三者各司其职。
```

#### 每种抖动谁扛——对照总表

| 抖动/场景                | 量级    | 扛它的机制                    | 要点                                          |
| ------------------------ | ------- | ----------------------------- | --------------------------------------------- |
| 网络下发忽快忽慢         | 几百 ms | ① jitter buffer               | 起播攒 240ms，之后随到随放                    |
| 网络突发（解码快于实时） | 秒级    | ② channel 背压 + ⑤ 削峰       | 满则阻塞；稳态库存压在 300ms                  |
| 播放线程偶发跟不上       | 几十 ms | 240ms 库存透支 + ③ auto_clear | DMA 断供自动发静音                            |
| 用户打断播放             | 即时    | ④ epoch 代数                  | 旧包自证过期，无需清队列                      |
| TTS 结束切 Listening     | 尾音    | ⑤ 水位计数                    | `sent <= played` 判排空，300ms 天花板保证敏捷 |

### 可迁移的设计模式

1. **分层抗抖**：网络抖动（几百 ms）用大缓冲扛，消费节奏间隙（几十 ms）
   用 DMA 扛，每层只管一个量级——单层扛所有抖动必然顾此失彼；
2. **有界队列 = 免费的背压**：`sync_channel(N)` 满则阻塞发送方；
3. **旁路数据用代数标记丢弃，而不是清空队列**：无竞态、无锁、幂等；
4. **水位计数必须全员配对**：任何一条发送路径漏加计数，条件就被永久
   毒化（开机提示音教训）；防御性写法是单向比较（`sent <= played`）
   而非严格相等；
5. **流畅性与响应性是天然权衡**：库存越深越流畅、排空越慢——
   "削峰稳态 + 深容量兜底突发"可以两全。

## 图 0：先理解敌人——抖动为什么造成卡顿

```
理想世界（无抖动）：
网络到达: ─■────■────■────■────■────■─►   每 60ms 一包
播放消费: ─▶────▶────▶────▶────▶────▶─►   每 60ms 播一包
           生产速度 == 消费速度，永远跟得上

真实网络（有抖动）：
网络到达: ─■────────■■■──────────────■■■─►   突发 + 空窗
播放消费: ─▶────▶────▶────▶────▶────▶───►   播放时钟恒定！
                         ▲
                         └─ 空窗期 DMA 断粮 → underrun → 嗒嗒声/爆音
```

**关键认知**：播放是硬件时钟驱动的（16kHz，每秒必须吐 64KB），网络是抖动驱动的。**两个时钟天然不同步，是所有问题的根源**。整套机制就是在这两个时钟之间垫缓冲。

## 图 1：全景架构——五个机制各守一层

```
 生产侧（快、突发）                              消费侧（慢、恒速）
 ═══════════════                                ═══════════════

 WebSocket线程         audio_loop线程              pcm_player线程    硬件
 ────────────         ──────────────              ──────────────    ────
                       ┌──────────────┐
  opus包(突发) ───────►│ 解码队列      │ ← 网络层缓冲
                       │ (VecDeque)   │
                       └──────┬───────┘
                              │ 取包 + opus 解码
                              ▼
                       ┌──────────────┐
                       │ ① jitter    │ ← 起播攒包 240ms
                       │   buffer    │   (tts start 先攒再播)
                       └──────┬───────┘
                              │ 攒够开闸，随到随放
                              ▼
                       ┌──────────────┐
                       │ ② sync_     │ ← 突发容量 1.5s
                       │  channel(25)│   满 → send() 阻塞 = 背压
                       └──────┬───────┘
                              │ (epoch, pcm)
                              ▼
                              ┌──────────────┐
                              │ ④ epoch     │ ← 打断快切
                              │   过期即丢    │
                              └──────┬───────┘
                                     │ output_data()
                                     ▼
                                     ┌──────────┐
                                     │ ③ TX DMA │ ← auto_clear
                                     │          │   underrun 发静音
                                     └────┬─────┘
                                          ▼
                                       扬声器
```

数据从左上往右下流，**越靠近网络缓冲越深，越靠近硬件兜底越硬**。

## 图 2：① jitter buffer——起播攒包

```
没有 jitter buffer（立刻播）：

tts start: 到一包播一包
到达:  ■ ■ ■ ■ ■ ...
播放:  ▶▶▶▶▶▶▶▶▶
储备:  0 ← 起播初期储备最薄，一次抖动就断粮 → 衔接卡顿

有 jitter buffer（攒 240ms 再播）：

时间 ─────────────────────────────────────────►
到达:  ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ...
       ├─ 攒包期 240ms ─┤├──────── 播放期 ────────
jitter:[■■■■■■■■■]       随到随放，但身后常备储备
播放:  ~~~~~~~~~~▶▶▶▶▶▶▶▶▶▶▶▶▶▶▶▶▶▶▶▶▶
                      ▲
                      └ 起播那一刻储备已有 240ms
                        之后抖动 <240ms 都伤不到 DMA
```

**本质**：把“起播初期最脆弱的阶段”用来攒弹药，用 240ms 的固定延迟换全程的流畅。

## 图 3：② channel 背压——突发不用写限速代码

```
网络突发：1 秒涌来 3 秒的音频量

audio_loop 解码飞快 ──► channel 入队 ──► pcm_player 恒速 1x 消费

前 1.5s:  channel ██████████ 逐渐填满（25 包 = 1.5s 容量）
1.5s 起:  channel 满 → send() 阻塞 audio_loop
          生产速度被强制拉低 == 消费速度
突发过去: channel 排空 → send() 不再阻塞 → 追赶积压

★ 有界队列 + 阻塞 send = 天然背压，一行限速代码都不用写
★ 内存也有上界：最多 25 包，不会 OOM
```

## 图 4：③ auto_clear——最后一道防线

```
DMA underrun 瞬间（TX 无新数据）会怎样？

auto_clear = false（旧行为）:
  DMA 输出: [最后32ms][最后32ms][最后32ms][最后32ms]...  循环重发!
  听感:     嗒嗒嗒嗒嗒嗒...（断流 1 秒 = 嗒 1 秒）
            ↑ 这就是之前"嗒嗒卡死"听感的来源之一

auto_clear = true（现配置）:
  DMA 输出: [最后32ms][静音][静音][静音]...
  听感:     声音轻轻停一下，数据来了无缝续上
```

**本质**：兜底机制不消除 underrun，只把 underrun 的**症状从灾难降为无感**。

## 图 5：④ epoch 代数——打断的竞态杀手

```
场景：TTS 播放中，channel 里还库存着旧音频，用户突然打断

打断瞬间 channel 内容（最多 1.5s 旧包）:
┌────┬────┬────┬────┬────┐
│ e0 │ e0 │ e0 │ e0 │ e0 │   全是 epoch=0 的旧包
└────┴────┴────┴────┴────┘
打断 → play_epoch: 0 → 1

pcm_player 之后收到的每个包:
  (e0, 包) → 0 ≠ 1 → 丢弃，不写 I2S   ✔
  (e0, 包) → 丢弃                     ✔
  (e1, 包) → 1 == 1 → 正常播放         ✔ ← 新一轮 TTS

对比方案"清空 channel":
  清完的一瞬间 audio_loop 可能恰好又 send 进一个旧包 → 竞态！
  代数比对：无竞态、无锁、幂等——旧包无论何时到达都会被认出
```

## 图 6：⑤ 水位削峰——流畅与响应的平衡术

```
水位 = pcm_sent_bytes - pcm_played_bytes（已送出未播完的量）

削峰前（channel 容量被当稳态库存用满）:
水位(ms)
1500 ┤      ██████████████████████████ ← 稳态顶格 1.5s
     │     ▲
   0 ┤─────┘
     └───────────────────────────► 时间
     tts stop 要从 1.5s 排到 0 → 切 Listening 慢 ~1.5s

削峰后（送包前检查：水位 ≥300ms 就暂停送包）:
水位(ms)
 300 ┤   ▲██   ▲██   ▲██   ▲██         锯齿波：
     │  ▌  ▌ ▌   ▌▌   ▌▌   ▌          送包涨一点 → 触顶暂停
 200 ┤ ▌  ▌▌            ▌▌            → 播放消耗降下来 → 继续送
   0 ┤▌
     └───────────────────────────► 时间
     tts stop 排空 ≤300ms → 切换快（~0.4s）
     突发时水位仍可冲高（channel 1.5s 容量兜底），只是稳态被压住
```

**本质**：1500ms 容量留给“突发”，300ms 锯齿留给“稳态”——一个管道，两种工况。

## 总表：每种抖动谁 来扛

| 抖动来源               | 量级   | 扛它的机制                      |
| ---------------------- | ------ | ------------------------------- |
| 消费节奏微间隙         | 毫秒级 | TX DMA 硬件缓冲                 |
| 断流瞬间（underrun）   | 任意长 | ③ auto_clear 发静音（降级症状） |
| 起播初期（最脆弱）     | <240ms | ① jitter buffer 攒包            |
| 网络突发/到包抖动      | <1.5s  | ② channel 容量 + 背压           |
| 打断后旧库存泄漏       | ≤1.5s  | ④ epoch 代数丢弃                |
| 稳态库存过深（排空慢） | —      | ⑤ 水位削峰                      |

**一句话总结**：网络和硬件两个时钟不同步 → 中间垫多层缓冲；每层只扛一个量级的抖动；兜底层（auto_clear）保证最坏情况也只是“停一下”而不是“嗒嗒响”；控制层（水位/epoch）保证缓冲不反过来拖累交互。
